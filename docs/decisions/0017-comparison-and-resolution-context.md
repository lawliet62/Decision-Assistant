# ADR 0017: 같은 후보의 조건 비교와 결정 당시 근거 보존

- 상태: Accepted
- 날짜: 2026-11-05
- 승인 근거: 같은 후보에서 조건·선호를 조정하고 선택·보류·포기 당시 근거를 보존한다는 Goal 범위. 저장 표현은 기존 모놀리스·JSONB snapshot 관례 안에서 선택했다.

## 문제

기존 화면의 조건 변경은 새 추천 생성으로 이어졌다. 제품별 사양 표와 선호 점수 입력이 분리되어 있고, Resolution에는 선택 ID와 이유만 있어 보류 후 조건을 변경하면 당시 비교를 복원하기 어려웠다. 카탈로그 누락을 모두 채우는 것이 이번 목표는 아니다.

## 결정

`Decision.comparison_state`에 현재 비교 조건, 비교에서 보류한 후보 ID, 직접 확인한 기능 정보를 저장한다. 최초 조회에서는 기존 추천의 조건으로 시작하며, 저장 이후에는 `ProductDiscovery.conditions`와 독립적이다. 추천 이력·추가 탐색의 원래 조건은 바뀌지 않는다. 비교 조건을 바꿔도 외부 API를 호출하지 않는다.

이어폰의 비교 조건은 예산·ANC·기본 연결 호환성이다. 기존 matcher로 판정하며, 표시 우선 정보는 가격·ANC·호환성·배터리·무게 중 선택한다. 표시 우선 정보는 점수를 만들지 않는다. 기존 Criterion 중요도는 기존 evaluator의 가중치로만 사용한다. 비교 조건은 기존 MinimumRequirement와 같은 참고 판정이며 평가용 Constraint나 자동 제외 규칙으로 변환하지 않는다.

직접 확인은 후보와 기능(`anc`, `Android`, `iOS`, `멀티포인트`)에 귀속한다. 확인 결과, 메모, 선택적 출처 URL, 서버 기록 시각을 보존한다. 수집 원문을 수정하지 않고 해당 기능 판정에만 우선 적용하며, 다른 플랫폼으로 전이하지 않는다. 확인값 해제는 원래 수집 근거로 돌아간다는 뜻이고, 반드시 UNKNOWN이 된다는 뜻은 아니다. URL은 참조용이며 가져오지 않는다. 공용 카탈로그와 자동 작업은 이 상태를 쓰지 않는다.

Resolution 생성 transaction에서 현재 Context, 후보, Criterion/OptionValue, Constraint/결과, 표시 사양, 비교 조건과 판정을 `comparison_snapshot`에 복사한다. 이 기록은 조회 시 재판정하지 않는다. 가격이 나중에 만료되거나 사용자 확인값·카탈로그가 바뀌어도 과거 판정을 바꾸지 않는다. V15는 nullable JSONB 열만 추가한다. 기존 Resolution의 당시 정보를 현재 값으로 소급 생성하지 않고 “고정본 없음”으로 표시한다.

변경 API는 Decision 소유권·편집 상태·expectedVersion을 검사한다. 새 화면의 결정 기록도 expectedVersion을 보내 충돌을 드러낸다. 기존 결정 기록 API 클라이언트의 optional version 호환성은 유지한다.

## 대안과 trade-off

- 최초 추천 조건 자체를 수정하면 새 추천 없이 비교할 수 있지만 과거 추천 이유의 의미가 바뀐다. 독립 상태는 이 문제를 피하는 대신 최초 추천 조건과 현재 비교 조건을 명확히 구분해야 한다.
- 확인값을 수집 ProductFact에 직접 덮어쓰면 단순하지만 원래 근거와 충돌을 검토하기 어렵다. 별도 확인 기록은 출처 구분을 유지한다.
- Resolution에 참조 ID만 남기면 저장량은 적지만 이후 변경·만료에 영향을 받는다. JSONB 복사는 후보 최대 5개의 제한 안에서 재현성을 우선한다. 별도 event store나 배포 단위는 도입하지 않는다.
- 한 단계 조건 복원은 현재 화면에서 직전 저장 조건으로 돌아가는 UX다. 전체 변경 이력·영구 undo는 제공하지 않는다. 결정 당시 고정본은 별도로 영속 보존한다.

검증과 사용자 평가 준비는 [비교 흐름 평가](../evaluations/comparison-flow-2026-11-05/README.md)를 따른다.

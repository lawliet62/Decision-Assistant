# 로그아웃이 403으로 거부되는 경우

## 증상과 기대 결과

운영 인수 시험에서 로그아웃 버튼이 보낸 `POST /logout`이 `403`으로 거부됐고, 직후 캐시를 우회한 `/api/v1/me`는 `200`을 반환했다. 로그아웃이 처리되지 않아 기존 인증 상태가 유지된 사례다. 다른 시도에서는 양식과 쿠키의 CSRF 토큰이 일치했고 로그아웃이 성공했다. 정상 흐름에서는 `POST /logout`이 Auth0 로그아웃으로 리다이렉트되고, 기존 앱 세션의 `/api/v1/me`는 `401`이어야 한다.

## 원인과 검증 범위

기존 양식은 화면을 열 때 읽은 `XSRF-TOKEN`을 `_csrf` 필드에 보관했다. CSRF 쿠키가 없는 상태에서 여러 조회가 겹치면 서로 다른 토큰이 발급될 수 있다. 늦은 응답 또는 같은 브라우저 프로필의 다른 탭에서 재인증한 결과가 쿠키를 바꾸면, 기존 화면은 예전 양식 값과 현재 쿠키를 함께 보낸다. 격리 시험에서 이 조합이 `403`을 재현했다. 운영에서 실패한 요청의 토큰 값은 수집하지 않았으므로, 당시에도 이 순서가 발생했는지는 확인되지 않았다.

[로그아웃 양식](../../frontend/features/auth/user-menu.tsx)은 제출 직전에 현재 쿠키를 읽는다. 쿠키가 없으면 기존 발급 경로를 사용하고 한 번만 제출을 재개한다. [브라우저 회귀 시험](../../frontend/e2e/logout.spec.ts)은 토큰 교체, 누락, 발급 실패, 발급 중 중복 제출을 확인한다. [Spring Security 회귀 시험](../../backend/src/test/java/com/decisionassistant/identity/LogoutSecurityTest.java)은 불일치 시 `403`, 일치 시 Auth0 리다이렉트 및 기존 세션의 `401`을 검증한다. 양식에 값을 넣은 뒤 브라우저가 요청 쿠키를 확정하기 전 값이 다시 바뀌면 `403`은 여전히 가능하다. 수정된 릴리스에서 실제 Auth0 로그아웃을 확인하는 작업은 운영 인수 시험에 남아 있다.

## 재발 시 확인 순서

1. 브라우저 Network의 **Preserve log**를 켜고 `POST /logout`과 직후 캐시를 우회한 `/api/v1/me`의 상태를 확인한다. `403` 직후 `200`은 세션이 현재 유효하다는 뜻이다.
2. 실패한 POST 자체의 Form Data에 `_csrf`, Request Cookies에 `XSRF-TOKEN`이 있는지 확인하고 두 값이 일치하는지만 기록한다. 값, 요청 본문, 전체 네트워크 기록은 공유 자료에 포함하지 않는다.
3. 성공한 로그아웃 뒤 뒤로 가기를 시험할 때 화면 모양과 새 API 응답을 구분한다. `/api/v1/me`가 `401`이면 서버 접근이 거부된 상태다. 새 OAuth 콜백과 함께 `200`이 되면 재인증 경로를 추적한다. 새 콜백 없이 `200`이면 세션 무효화를 우선 확인한다.

외부 로그 허용 목록은 일반 CSRF 거부와 OAuth 콜백 오류를 전달하지 않을 수 있다. Cloud Logging에 오류가 없더라도 브라우저에서 확인한 HTTP 상태와 요청 순서를 근거로 사용한다.

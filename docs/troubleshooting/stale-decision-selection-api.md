# 결정 전체 선택에서 403이 반환되는 경우

2026-11-10 로컬 개발 환경에서 목록·상태 건수 조회는 성공하지만 결정 전체 선택은 403과 빈 본문을 반환했다. 당시 Spring 프로세스는 선택 API를 도입한 PR #49 병합보다 먼저 실행 중이었다. 같은 서버에서 UUID가 아닌 다른 경로도 403을 반환했고, 현재 코드를 새로 실행한 별도 synthetic DB 환경에서는 `GET /api/v1/decisions/selection`의 단일·복수 상태 요청이 200으로 성공했다. 확인한 원인은 실행 중인 backend가 갱신된 frontend보다 오래된 버전인 것이다. 모의 backend를 쓰는 브라우저 테스트와 최신 코드 기반 integration test만으로는 이 불일치를 발견하지 못했다.

운영자는 실행 중인 backend의 소유 세션과 진행 중인 작업을 확인한 후 정상적으로 중지하고, 최신 backend 코드를 같은 환경 설정으로 다시 실행한다. frontend와 backend는 함께 갱신한다. DB volume을 지우거나 초기화할 필요는 없다. 재시작 후 `/api/v1/me`, 목록 및 선택 API와 화면의 상태별 선택을 확인한다. 다른 독립 세션이 worktree나 프로세스를 사용 중이면 그 세션과 조정한다.

403은 권한이나 다른 설정 문제에서도 발생할 수 있다. 프로세스 시작 시각과 실행 코드 버전이 일치한다면 인증·서버 로그·실제 응답을 별도로 조사하며, 무조건 구버전 문제로 단정하지 않는다. local synthetic 검증은 [배포 smoke](../../deploy/README.md)의 실제 backend 선택·토글 확인을 포함한다.

# 제품 탐색 A안 재실험 결과

2026-09-30 KST. 기존 방식 15회와 A안 15회, **총 30회를 완료했다.** 모든 실행에 해당 worker의 완료 계측이 있다. 초기 worker 혼입 실험은 [별도 무효 기록](initial-observation.md)으로 보존하고 아래 집계에서 제외했다.

**A는 빈 검색을 줄였지만, 원하는 추천 서비스의 품질에는 아직 부족하다.** 출처를 사람이 보강 검토했을 때 조건에 맞는 서로 다른 후보를 2개 이상 확보한 조건은 0/15에서 1/15로 증가했다. 앱 자체가 사양 근거까지 확보해 기본 추천 2개를 제시한 조건은 양쪽 모두 0/15였다. B/C나 리뷰 수집으로 즉시 확장하기 전에 현재 가격·사양 검증과 설명의 결함을 먼저 다루는 것이 타당하다.

## 실행과 유효성

- [고정 입력](../../../scripts/discovery-evaluation/cases.json): 5개 제품군 × 3개 조건. 기존 방식 `1bdc554`, A `994dd90`의 별도 JAR를 사용했다. 이후 커밋의 backend 실행 코드는 A와 동일하다.
- 동일한 Gemini `gemini-3.5-flash-lite`, Serper·Firecrawl, 공식 판매처 정책, 회당 검색 1·수집 최대 5·AI 최대 1을 사용했다. 파서 수용 기준·프롬프트·모델·사양 판정을 실험 중 변경하지 않았다.
- 시작 전에 개발 backend/frontend가 이미 꺼져 있었고 DB에는 다른 애플리케이션 연결이 없었다. 평가 서버 하나만 실행했고 종료 후 평가 프로세스와 DB 연결이 사라진 것을 확인했다. 개발 서버의 기존 종료 상태를 유지했다.
- 기준 방식은 07:03:41~07:07:42에 15개를 완료했다. A는 07:07:52~07:10:14에 5개를 완료한 뒤 Firecrawl 429로 중단했다. 실패한 조건을 다시 실행하지 않고, 07:13:37~07:23:40에 미실행 10개만 이어갔다. 승인된 총 30회 범위 안이다.
- 초기 조건 생성 간격은 최소 13초였다. A 후반 10개는 65초로 늘렸으며 추가 429가 없었다. [Firecrawl 공식 문서](https://docs.firecrawl.dev/rate-limits)는 Free의 수집 한도를 분당 10회로 설명한다. 실제 계정 플랜이나 429의 상세 원인은 로그만으로 확정하지 않았다. 변경한 것은 평가 조건 사이 간격이며 서비스 내부 병렬 수집·호출 정책은 동일하다.

각 조건 1회뿐이며 검색 순위·페이지·재고·LLM 출력의 시간 변동이 있다. 중간 요청 빈도 변경도 있어 처리량이 동일한 환경의 통계 실험은 아니다. 실패를 포함한 관찰 결과이며 통계적 우위나 전체 시장 품질을 주장하지 않는다.

## 2. 필수 조건 오판과 근거 없는 주장

- A의 최소 사양 검사 5개(ANC 3개, RAM·SSD 각 1개)는 전부 `UNKNOWN/MISSING`이었다. 잘못된 `MET`은 관찰되지 않았지만 `MET` 판정 자체가 0개여서 충족 판정의 정확도를 평가할 수 없다.
- LG 노트북 후보의 공식 기본 사양은 8GB·256GB로 요청한 16GB·512GB에 미달한다. 앱은 `UNKNOWN`으로 남겼고 AI 설명도 미달을 알리지 않았다. 충족 오판과 **미달 탐지 실패**를 구분한다.
- LG의 1,290,000원은 구조화 Offer에는 일반 가격처럼 있지만 화면에는 회원할인가로 표시된다. 회원·조건부 가격을 제외하는 현재 정책의 검증 누락 1건이다. 원문에 존재하는 숫자만으로 조건 없는 비교 가격이 되지는 않는다.
- ANC 후보 3개 설명은 출퇴근·통화·운동·음악 적합성을 근거 연결 없이 단정했다. 기능 지원과 용도별 성능 검증은 다르다. 이 3건을 근거 부족으로 기록한다.
- T17APP은 최소 사양을 지정하지 않은 조건에서 `RECOMMENDED`가 됐지만 앱 근거와 이번 직접 검토로 iOS 호환성까지 확인하지는 못했다.

AI 제안 사실 10개 중 6개가 인용 검사를 통과하고 4개는 `UNBOUND_EVIDENCE`로 제외됐다. 가격 등 일반 사실도 포함되며 필수 사양 충족 수와 같지 않다. 이벤트는 제외한 사실의 종류까지 남기지 않으므로 모든 누락을 AI나 검증기 어느 한쪽 탓으로 확정하지 않는다.

## 4. 대기 시간·호출·토큰·한도

| 지표 | 기존 방식 | A |

| 사용자 관찰 시간 합계 | 109.553초 | 244.064초 |
| queue 중앙값 / 최대 | 0.729초 / 1.600초 | 1.186초 / 1.877초 |
| worker 실행 중앙값 / 최대 | 1.645초 / 31.662초 | 12.718초 / 29.909초 |

합계는 **검색 30·수집 47·AI 5회, 입력 44,497·출력 3,559 token**이다. 승인 상한 검색 30·수집 150·AI 30 안에서 끝났다. 수집 호출에는 실패 시도도 포함하며 provider의 실제 청구 credit과 동일한 숫자라고 가정하지 않는다. 출처를 직접 검토한 웹 조회는 서비스의 Serper·Firecrawl·Gemini 호출과 분리했다.

사용자 관찰 시간은 Decision 생성 요청부터 최종 상태 확인까지다. 조건 사이 의도적 간격과 재개 전 점검 시간은 제외한다. 실제 전체 재실험은 약 19분 59초, 기준 구간 약 4분 1초, A의 두 실행 구간 합계 약 12분 24초다. A 최초 시작부터 최종 종료까지는 중단·점검 약 3분 23초를 포함해 약 15분 48초다.

기존 방식의 짧은 시간은 대부분 초기에 후보를 못 찾고 끝났기 때문이다. A의 수집·AI 사용 증가는 다음 단계까지 도달한 실행이 늘어난 결과다. 호출 상한이 같아도 실제 사용량이 같지는 않다. 낮은 단일 요청 지연만으로 연속 요청의 한도 문제가 해결됐다고 보지 않는다.

## 5. 설명 유용성

후보 5개 설명은 **0점 3개, 1점 2개, 2·3점 0개**였다. 평균 0.4/3점이며 서로 다른 조건에 반복된 모델도 별도 설명으로 평가했다. 원래 조건의 설명은 용도를 나열하는 데 그쳤고, 사양과 용도의 관계·제약·미확인 사항을 함께 설명하는 결과는 없었다. 기준 방식은 설명 자체가 없어 해당 없음이다. [후보별 판정](source-review.md)과 [사용자용 빈 평가표](human-review.md)를 제공한다.

## 후속 우선순위

1. **기존 검증의 정확성:** 회원 가격과 일반 가격을 구분하고 공식 기본 사양을 누락하지 않도록 수집·추출·제품 연결을 점검한다. 이미지에만 있는 근거는 별도 취급하며 OCR 도입을 당연한 전제로 삼지 않는다. 설명도 확인된 사양과 미확인 사항에 맞추는 것이 우선이다.
2. **공식 개별 상품 확보:** 질의 결과를 개별 상품 경로로 연결하는 방법과 URL 동치·리다이렉트 판정을 작은 범위에서 검증한다. 검색 계획(B)이 도움될 여지는 있지만 파서 결함을 호출 증가로 가리면 비용만 늘 수 있다.
3. **B/C·리뷰 수집 보류:** 기존 예산 1/5/1 안의 정확성 개선을 먼저 평가한다. 그 후에도 공식 상품 확보가 반복적으로 막힐 때 B 또는 C의 추가 비용과 품질 이득을 별도 실험한다. 리뷰 수집의 비용 대비 이득은 이번 실험으로 검증하지 않았다.

이는 후속 제안이며 런타임의 가격 정책·사양 검증·프롬프트를 이번 평가 중 수정하지 않았다. A와 계측은 검증 가능한 개선이지만 이 결과를 서비스 출시 품질 충족으로 표시하지 않는다.

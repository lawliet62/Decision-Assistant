# 카탈로그 MVP 초기 검증과 캐시 판단

## 결론과 검증 범위

클릭으로 조건을 선택하는 진입을 유지하고, PostgreSQL의 사전 검토 제품을 읽는 경로를 구현했다. 사용자 요청의 외부 검색·수집·LLM 호출은 0회다. 초기 제품 5개 중 2개의 ANC·기본 호환성 공식 근거를 등록했다. 나머지 3개의 근거를 추정해 채우지 않았다.

이번 결과는 범위가 정해진 추천과 정보 수명 경계의 구현 검증이다. 과거 15조건 실시간 검색 평가와 대상 제품·조건·가격 확보 방식이 달라 품질 상승률로 직접 비교할 수 없다. 실제 Firecrawl 가격 갱신의 성공률, 2주 변동률, 관리 시간은 아직 측정하지 않았다. 일간 갱신은 초기 운영 가설이다.

## 초기 등록 근거

공식 판매 URL 5개에 각각 1회 직접 HTTP GET을 수행해 HTTP 200과 JSON-LD 제품명을 확인했다. [짧은 점검 결과](source-inspection.json)에 URL·최종 URL·제품명·제품 그룹·시각만 남겼으며 HTML 원문은 보존하지 않았다. 이는 Firecrawl 경로의 성공이나 strict 가격 파서 통과 검증을 대신하지 않는다. 앱 seed에는 가격을 넣지 않았다.

이후 같은 5개 URL을 각 1회 더 읽어 실제 `OfficialProductParser.inspect`에 전달했다. [가격 파서 점검](parser-probe.json)은 **5/5 통과, 등록 identity 5/5 일치**다. 확인 가격은 T13 ANC 28,200원, HT16 31,800원, HT19 50,900원, T13 Pro 21,900원, T17 APP 29,900원이었다. 2026-10-06 05:45 UTC의 단발 관측이며 앱 DB에 주입하거나 가격 seed로 사용하지 않았다. 전체 직접 GET은 10회, Firecrawl·AI 호출은 0회다. 따라서 고정 URL과 파서 연결은 확인했지만 Firecrawl의 HTML 반환·지연·가동률은 여전히 별도 검증 대상이다.

| 제품 | 등록한 공식 사양 | 보류한 내용 |
| --- | --- | --- |
| QCY T13 ANC | ANC 지원, iOS/Android 기본 호환성 | ANC 성능 점수·주관적 음질 |
| QCY T13 Pro | ANC 지원, iOS/Android 기본 호환성, IPX4 | 마케팅상의 감쇠 수치를 제품 간 성능 점수로 환산 |
| QCY HT16 / HT19 | 없음 | 지역별 N50/N70 이름과의 동일 모델 연결 |
| QCY T17 APP | 없음 | T17의 사양을 APP 모델에 전용 |

사양 근거는 [QCY T13 ANC 공식 페이지](https://www.qcy.com/products/qcy-t13-anc), [QCY T13 Pro 공식 페이지](https://www.qcy.com/products/qcy-t13-pro)에서 확인했다. 등록 manifest에 짧은 원문 인용과 확인 시각을 보존한다. 운영자가 검토했어도 사용자 확인 상태로 승격하지 않는다. 한국 판매 제품과 공식 모델 연결의 오류 제보가 있으면 revision을 올려 정정한다.

## 캐시 없는 DB 기준 측정

2026-10-06 로컬 Windows, warm JVM, MockMvc + Testcontainers PostgreSQL 17에서 비교 생성 POST를 측정했다. 각 제품 수마다 5회 준비 요청 후, 동시성별 30회 요청이다. DB 조회뿐 아니라 조건 판정·후보 저장·응답 직렬화를 포함하며 브라우저·인터넷·운영 서버 지연은 제외한다. [기록한 표본 요약](benchmark.json)을 기준으로 한다.

| 활성 제품 | 동시 요청 | 요청 수 | p50 | p95 | 최대 |
| --- | --- | --- | --- | --- | --- |
| 5 | 1 | 30 | 97.8ms | 119.6ms | 138.8ms |
| 5 | 5 | 30 | 156.7ms | 184.1ms | 193.1ms |
| 30 | 1 | 30 | 92.7ms | 124.9ms | 127.1ms |
| 30 | 5 | 30 | 126.2ms | 141.0ms | 141.0ms |

제품 수 증가에 따라 뚜렷하게 느려지는 결과는 없었다. 작은 표본과 JVM 준비 효과 때문에 30개가 더 빠르다고 일반화할 수 없다. 현재 규모에서 별도 캐시의 유의미한 추가 이득을 입증하지 못했으므로 도입을 유보한다. 캐시 대비 실험은 하지 않았으며 이 수치를 캐시 개선율로 표현하지 않는다. 운영 지연이 생기면 `catalog.db.read`와 전체 요청 시간을 분리해 확인하고 실제 병목에 대해 비교 실험한다.

재현: `node scripts/gradle.mjs integrationTest --tests '*CatalogApiIntegrationTest'`. 결과는 `backend/build/reports/catalog-benchmark.json`에 생성되며 실행 환경에 따라 달라진다.

## 회귀 검증과 운영 후 평가

- 단위 검증: 가격 24시간 경계·미래 시각, 소프트웨어 30일·하드웨어 90일, 실패 시 시각 보존, 모델 변경 가격 초기화, manifest revision과 초기 공식 근거.
- PostgreSQL/API 검증: V11 migration과 seed 기동, 외부 동의 없는 생성, 타인 접근 차단, 수용 후 근거 보존, 만료 가격의 예산 판정 차단, 수집 실패·월 상한·동시 worker의 중복 방지·모델 불일치.
- Chromium: 새 카탈로그 흐름을 포함한 28개 E2E 통과. 기존 실시간 추천·직접 입력·비교·선택·회고 경로도 포함한다. mock provider 결과이므로 실제 수집 성공률과 구분한다.
- 주기 분석 도구는 fixture로 실패 분모·가용성·예산 오판·사양 점검 기한을 검증한다. 실제 14일 관측 결과는 아니다.

다음 운영 평가는 [카탈로그 운영](../../catalog-operations.md)의 호출 상한 100회 내에서 5개 제품을 2주 관측한다. 판매가·판매 가능 여부 오류와 UNKNOWN 비율, 주당 수동 점검 시간을 함께 기록한다. 처음부터 3/7일 갱신으로 늦추거나 캐시 TTL을 가격 유효기간으로 사용하지 않는다.
